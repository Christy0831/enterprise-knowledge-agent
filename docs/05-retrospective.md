# 05 · 难点、学习收获、用时与下一步

## 最难的问题

难点不是连上模型，而是区分“能给出一个带引用的答案”和“根据证据可靠地完成任务”。开发中确实出现了有真实引用但问题完全不相关的回答：资料外问题被Mock扩展查询命中报销制度，逐字引用校验无法识别语义不相关。这次失败促使评估加入资料外状态和引用集合检查，也明确保留人工语义审核边界。

第二个难点是模型服务差异。DeepSeek的Responses兼容接口不能靠 `parallel_tool_calls=false` 保证单工具返回。执行器因此按实际工具调用计数，接受多个读取，区分同轮预先产生的动作和观察后的新决策，防止日志错误地描述执行顺序。

## 有价值的取舍

- 使用原生Python循环，把模型选择、工具执行、结果反馈和停止条件直接写清楚，便于评审和解释。
- 小知识库采用BM25，无向量数据库及embedding下载成本；把同义改写作为可观察的模型动作。它不等于通用语义检索。
- 检索与读取分开，引用只来自本轮成功读取的原文；预览、历史回答和读取失败均不能成为证据。
- 未知优先级保持未知，不把“较新”擅自解释为“更有效”；冲突无法消解时追问也是合理结果。
- 保留真正运行产生的失败记录，比只留最终成功输出更容易解释改进依据。

## 学习收获

RAG中检索、上下文拼接和回答生成可以成为Agent工具，但必须由真实模型根据观察选择下一步，才有题目要求的动态决策证据。写一个规则分支或自动重试，不能因日志看起来像ReAct就声称满足要求。

工程测试与模型评估也不同。前者验证调用、状态、预算和引用等约束；后者要检查模型面对不同工具结果是否合理调整动作、回答是否受原文支持，以及失败时是否承认无法完成。

## 下一步及未完成边界

后续React界面带来了新的证据边界：Token增量不能绕过引用校验，因此页面必须区分草稿与正式答案；错误重试、断开和取消不能把残留草稿当成完成。实现采用真实上游SSE，未用打字机动画代替流式。界面仅是用户追加的本地交互扩展，不改变题目无需线上部署的范围。
